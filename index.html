Adversarial testing for learned robot policies

Robots are learning to move. We find the exact condition where they fall.

Teeter stress-tests trained robot control policies in simulation. It searches the physical conditions you declare (pushes, slopes, sensor lag, weak motors) for the ones that break your rules, reduces the worst to the smallest condition that still causes them, and hands back evidence anyone can re-run.

A trained policy has no branches to read and no lines to cover. The only way to learn where it breaks is to go looking: on purpose, in the physics, against a rule you can argue with.

TT-101

The gap

A policy that passes your test suite has only passed your test suite.

A modern robot does not run hand-written control code. It runs a neural network trained in simulation that maps what it senses to what its motors do. It holds under the conditions it was trained on, offers no guarantee anywhere else, and nothing inside it signals when a situation is unfamiliar.

That breaks the instincts carried over from software testing. An ordinary program has branches to enumerate, so 100% coverage means something. A network has none: line coverage of its inference code reaches 100% after one forward pass and tells you nothing.

The space of situations is a continuous volume. A hundred scripted scenarios tell you about a hundred points inside it.

TT-102

Why now

2027-01-20

Learned safety functions stop being self-certifiable.

On that date Regulation (EU) 2023/1230 replaces the Machinery Directive in every member state at once. Where machine learning ensures a safety function, the machine falls under Annex I Part A, and a notified body must be involved even if every harmonised standard is followed.

What counts is not settled. Whether a legged robot's balance controller is a safety function is an open question, ISO 25785-1 for robots that balance actively is still being written, and the delegated act defining adequate evidence is not due until 2028.

A manufacturer can keep a separate, conventionally certified safety layer beside the learned policy, and many will. Teeter is useful either way: a policy that falls over is worth knowing about whether or not an assessor asks.

TT-103

A run

Five stages, one question: where does it fail?

  1. 1

    Ingest

    Your policy and robot model, loaded into deterministic simulation. Seeds, simulator version and file hashes are recorded with every run.

  2. 2

    Perturb

    Each test is one point in the space you declared: a specific friction, slope, latency, payload and push, applied together.

  3. 3

    Search

    Uniform sampling covers the volume. A directed search then fits a distribution to the most severe results and samples again, spending budget where violations are dense.

  4. 4

    Detect

    Every step of every trajectory is checked against your predicates. A run is flagged only when a rule you wrote evaluates true.

  5. 5

    Reduce

    The most severe failures are each walked back toward nominal for as long as the rule still fires, so what you receive is the smallest condition that still breaks the policy.

The axes, rules, budget and reduction are the published campaign's, read from its record. The record keeps no config file, so the robot, policy, seeds and grace periods are what faultline init writes: this file is a reconstruction, not the one that ran. The simulator version is never set here; it is recorded with each run. The command-line tool keeps its working name, faultline, until the software is renamed.

TT-105

The rule

A failure is a rule you wrote, not a judgement we made.

Every violation is an explicit predicate over the trajectory. No learned classifier sits between the run and the verdict, so you can read the line that flagged a run and argue with it. Predicates see four signals and nothing else: tilt_deg, height_m, contact_force_n and joint_vel_rads.

TT-107

Trust

Built to be re-run by someone who wants us to be wrong.

Evidence about a robot is worth what survives a hostile reader. So every result is constructed to be checked, not believed.

  • Re-runnable

    Three seeds recorded separately: sampler, simulator, policy. A replay re-simulates the run and checks it against the recorded trajectory hash. The replay at the top of this page breaches at 1.26 s, the time the campaign recorded.

  • Rules you wrote

    A violation is a predicate over four measured signals, with a threshold and a grace period. No learned classifier decides what counts as failure.

  • The smallest case

    The worst failures are reduced until the rule would stop firing, so you receive the least condition that breaks the policy, not the most dramatic one.

  • No word we can't defend

    Nothing we produce calls a policy safe, verified or compliant. The harness's own test suite fails if a generated report makes an affirmative safety claim.

What you receive

Engineering report

Failures grouped by mode, the region of the space each mode occupies, and the minimal reproducing case for every one.

Safety-case appendix

Method, the declared space and how much of it was covered, every predicate, and the run manifest. Written for someone assessing the evidence.

Run archive

Seeds, simulator version, and hashes of the configuration and model for every run. A replay re-runs the simulation and checks it against the recorded trajectory hash.

Simulator
MuJoCo 3.12.0, pinned exactly. Contact solvers change between minor versions.
Robot models
MJCF. URDF loads with a warning: it carries no contact parameters or actuator dynamics.
Policies
ONNX graphs and TorchScript archives, each an optional extra.
Predicates
YAML: a signal, an operator, a threshold and a grace period.
Output
Markdown report and appendix, run manifest, campaign and report JSON, a trajectory CSV per failure mode.
Where it runs
On your machines, as a Python package. The archive holds results and hashes, never the policy's weights.

TT-108

Status

What we can show, and what we can't.

  • CanName the conditions under which a policy broke, reduce the worst to their smallest form, and hand over an archive where every run re-executes from its seeds.
  • CannotShow that failures are absent. A search finds them; no number of runs without one proves there are none left.
  • Will notCall a policy safe, verified, validated or compliant, or imply the output satisfies a notified body. Nobody can currently say what does.
  • TodayOne robot model, and a baseline policy that holds a stance rather than a trained one. No customers, no pilots, no hardware tests, one person.

TT-109

Where this goes

Every learned machine that ships should arrive with a list of the conditions that break it.

Learned policies are leaving the lab for warehouses, farms, factories and homes. Each will meet floors, loads and shoves nobody trained it on. We want those found in simulation, by someone looking on purpose, before they are found in the world.

  1. Now

    One robot, one campaign

    The harness runs end to end on our own stand-in quadruped. Everything on this page comes from it.

  2. A · ~90 days

    Someone else's robot

    Done when someone who is not us can point it at their own robot and policy, run a campaign, and compare two checkpoints.

  3. B · ~90 days after A

    Calibration

    Done when a campaign emits a calibrated interval, shown correct on synthetic ground truth, with the limits of what it demonstrates written down.

  4. C · months ~7–12

    The first partner

    A failure mode found in a real customer's policy that they did not know about, which they then reproduced on hardware.

This is the plan in docs/roadmap.md, not a promise. None of A, B or C is done yet.
